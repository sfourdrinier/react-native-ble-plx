# Unified BLE 4.0 lab and procurement manifest

manifests/unified-ble-4.0-lab.json is the version-controlled authority for Phase 0 UB4-LAB-PROCUREMENT. It records the mandatory 4.0 hardware matrix, typed evidence, acquisition readiness, scenarios, gates, and live-evidence actions. The manifest is fail-closed: no support label, live gate, physical allocation, or procurement fact is trusted merely because it is written in a profile.

Validate the manifest and print its derived state:

    node lab/scripts/validate-lab-manifest.js
    node lab/scripts/validate-lab-manifest.js --summary
    node --test lab/tests/lab-manifest-validator.test.js

The validator uses the schema first, then enforces the cross-record rules that JSON Schema cannot express:

- `asOf` is the explicit review instant. Generated, observed, inventory-history, and confirmation timestamps cannot postdate it (or the validator clock); every evidence record’s `revalidateBy` and every profile’s next review date are derived exactly from a declared cadence. A date in 2099 cannot make an old fact look current.
- Completed lab evidence is accepted only when it binds to an existing, independently valid `evidence/v1/records/*.json` manifest through a descriptor-backed `O_NOFOLLOW` read, regular-file `fstat`, canonical realpath containment, and recomputed manifest SHA-256. The closed mapping for each lab evidence kind derives its level from passed source scenario kind, level, and provenance; lab text cannot self-report either. Every cited lab asset is immutably bound to the source host or peripheral `safeId` with its required role and class. A deferred 4.1 physical controller additionally binds its exact controllable source identity and every declared controller feature. Fixtures, missing paths, path escapes, symlinks, stale manifests, and self-authored lab text do not constitute proof.
- Support labels, levels, and availability are derived from those validated completed evidence bindings with exact profile-target matching. A Preview requires completed L2 compile/package and L1 deterministic-TCK records. Live Preview additionally requires L4 physical-radio proof; Supported requires the complete L4 live matrix; Reliability-qualified additionally requires L5 reliability evidence.
- Deferred platform work is recorded only in its dedicated 4.1 scope decision, never in the 4.0 lab matrix, gates, or evidence labels. The required Windows, Ubuntu, Fedora, macOS, Apple mobile/TV, Android, TV, Fire TV, and Chromium macOS/Windows profiles must remain present. Every ordinary live scenario names a physical host/device role and a fixed-function physical-peripheral role.
- The canonical 13-profile specification fixes every 4.0 profile’s platform, backend, host runtime, asset set, and scenario set. The fixed live-evidence action specification fixes every action’s G4 membership and typed completion predicate, so relabeling a profile, deleting an action, or resolving an action with unrelated evidence cannot change live-gate readiness.
- Inventory uses an explicit transition history. Every procurement record is bound to one asset: orders and reservations bind the acquisition asset, bookings are active at `asOf`, and setup profiles bind the configured asset. G0 has no lab-hardware membership and cannot be blocked by missing hardware. For each live-evidence action, procurement still requires an active reservation or dated delivery path at `asOf`, an approved monetary amount and currency (or a documented `not-required` budget), distinct primary and fallback suppliers, a replacement policy, location, escalation, and setup. Each asset also records required cable/accessory access, remote-access viability, and whether it is shareable; unverified access facts block its associated live evidence. Setup profiles contain firmware/OS, toolchain, signing or developer-mode, driver/SDK, and reproducible-setup facts. Missing facts are explicit blockers, not unverified reference sentinels.
- Gate satisfaction is independently derived per asset: G4 requires received, configured, available physical assets plus validated physical evidence and the exact live scenario proof. An asset’s own `satisfiedGateIds` cannot make it ready. The summary reports G0 separately from the remaining live-evidence actions.
- The scenario taxonomy is closed. 4.0 may run deterministic fault injection, but it cannot claim controllable physical faults. Fixed-function peripherals prove ordinary vertical slices only. The deferred 4.1 physical-controllable-fault scenario requires a passed L4/L5 `live-radio` fault-injection scenario using a physical controllable provider with every declared controller feature.

The current live-evidence matrix deliberately remains blocked, unclaimed, and unverified. Its only evidence record is an explicit missing-inventory observation. It does not invent a device owner, supplier, order, location, booking mechanism, escalation contact, physical allocation, or live-radio artifact. Resolve a live-evidence action only by adding the corresponding typed registry records and completed evidence; do not replace missing facts with placeholders.
