# Unified BLE evidence manifests v1

This directory is the Phase 0 evidence authority for backend/platform support claims. It uses strict JSON because Node can parse it without adding a dependency. The schema documents the record shape and the validator enforces all cross-field safety rules that JSON Schema alone cannot express.

Validate one or more records from the repository root:

```sh
node scripts/evidence/validate-evidence-manifest.js --at 2026-07-26T03:58:20.000Z evidence/v1/records/*.json
```

`--at` makes revalidation-expiry checks reproducible. Omit it in normal CI to validate against the current time. `pnpm validate:evidence` validates every current record, and is a required package-build, release-script, PR-CI, and publish-CI gate. Fixtures are deliberately validated only by the focused Jest suite; they never become a release record.

## What a record proves

Each record binds a claim identity/revision to backend, platform, host, runtime, toolchain, source commit, canonical dirty-state disclosure, commands, result artifacts, capability limitations, owner, revalidation policy, boundary compatibility, and supersession history. Every scenario names its command IDs, result artifacts, and execution window. A passed scenario requires zero-exit commands, must include each command’s result artifact, and must fit inside both the command and record time windows. Execution, command, and scenario timestamps allow at most five minutes of future clock skew relative to validation time.

Artifacts are typed as `command-result`, `command-receipt`, `package-artifact`, or `source-state`. Artifact paths are restricted to `evidence/v1/`, must be canonical regular files, cannot traverse a symbolic-link component, and have their SHA-256 digest recomputed by the validator. Manifest descriptors receive the same no-symlink containment check. A verified package artifact must point to a `package-artifact` with an identical package type, path, and digest. Tarballs must be parseable package archives containing `package/package.json` and payload files; native binaries need native magic plus Node ABI metadata; build outputs need matched CommonJS and ESM entrypoints beneath `lib/`.

Every non-historical command must have a canonical `command-receipt` generated by `scripts/evidence/run-evidence-command.js`. Its digest binds the exact non-shell argv, allowlisted environment, registered command profile, executable version/digest, command/scenario identity, timestamps, exit code, result-artifact digest, Node module ABI, and repository remote/commit/dirty-status digest. `toolIdentity` is no longer evidence by itself. Fixture-only profiles cannot certify a non-fixture claim. Historical `reported-unverified` records intentionally have no receipt and remain blocked L0 only.

Dirty source records carry the Base64 form of the canonical `git status --porcelain=v1 -z` payload in their `source-state` artifact. The validator accepts only valid porcelain XY state transitions, then recomputes the dirty flag, path count, and SHA-256 from that payload rather than trusting record self-reporting.

Proof provenance is deliberately separate from level:

| Provenance | Required level | Meaning |
| --- | --- | --- |
| `environment` | L0 | Toolchain/environment availability only. |
| `mock` / `deterministic` | L1 | No radio claim. |
| `compile` | L2 | Build/package proof only. |
| `system` | L3 | System/ABI/probe proof without a physical radio journey. |
| `live-radio` | L4 or L5 | Physical-radio proof. |
| `reported-unverified` | L0 | Historical assertion with missing reproducible artifacts; never a passing support proof. |

The validator rejects any attempt to relabel compile, mock, deterministic, or system evidence as live evidence. The manifest-level proof level must equal the strongest passed scenario, preventing both overstatement and ambiguity.

## Published support labels

The validator encodes the controlling plan’s distinct support rules:

| Label | Enforced minimum |
| --- | --- |
| Experimental | No stability promise; lower-level records remain explicit. |
| Preview | Passed L2 compile/package proof, passed L1 deterministic TCK, a verified package artifact, and structured limitations. |
| Live Preview | Every Preview requirement plus a passed physical-peripheral L4+ live-radio vertical slice. |
| Supported | Live Preview plus a declared capability/scenario/environment matrix that links every non-unsupported capability to passed physical L4+ proof on the declared environment. |
| Reliability-qualified | Supported baseline plus passed, capability-linked L5 live-radio background, reconnect, and soak scenarios; each must retain at least 60 seconds of captured duration and their receipt-bound start/end events must progress in that order without overlap. |

No deferred 4.1 environment may be marked `Live Preview` (or higher) by the 4.0 evidence system. Controller features are a closed taxonomy. A fixed-function peripheral may substantiate only ordinary live vertical slices; controller-dependent scenarios must use a matching deterministic virtual controller for mock/deterministic proof or a physical controllable fault-injection peripheral for live-radio proof. Deterministic fault injection is never relabelled as live radio.

`native-abi`, `electron-ipc`, and `react-native-turbomodule` boundaries declare a version range and a passed handshake scenario. The validator checks the subject host role and boundary process pairing, canonical ABI/protocol identifier, exact Electron/RN identifier-version agreement, range containment, `nativeOrIpc` version, and L3+ system handshake proof. Reported-unverified historical records keep an explicit `unreported` exception and remain non-gating.

Every passed L4/L5 live-radio scenario must name a physical peripheral, a concrete adapter, and a live-radio execution. L5 background, reconnect, and soak proof therefore cannot be detached from hardware or compressed into instant scenarios. TCK and legacy package scenarios require their corresponding registered receipt profile; shell commands, interpolation, and generic test invocations cannot be certified. Historical `reported-unverified` records are restricted to blocked L0 reported scenarios.

Collections validate claim/revision uniqueness, contiguous in-claim revisions, reciprocal supersession references, cycle freedom, and the captured-at revalidation cadence. `nextDueAt` cannot exceed the declared cadence from capture.

## Stable GA publication gate

Final SemVer publication also requires a separately versioned manifest at
`evidence/v1/releases/vX.Y.Z.json`, validated by
`scripts/evidence/validate-stable-release.js`. The gate reuses the manifest
validator for every required claim, then verifies that the release tarball,
source commit, tag, approved successful `ci.yml` run, generated support matrix,
Section 31 reconciliation, and governance, security, SBOM, license,
provenance, and package-shape receipts are mutually bound. Every required claim
must be clean, passed, receipt-backed, and meet its plan-bound floor (`Preview`
for deterministic proof and at least `Supported` for platform/host claims); no
blocked, skipped, failed, or `reported-unverified` scenario can satisfy GA.

The stable manifest is intentionally absent until those artifacts genuinely
exist. This makes a current final tag fail closed without changing the
Experimental prerelease path or relabelling any current record.

## Fixtures and tests

`fixtures/` includes valid compile, mock, system, live-preview, reliability, and reported-unverified records. `adversarial-cases.json` records declarative single-manifest regressions. The focused Jest suite also constructs temporary symbolic-link directories and multi-record DAGs to exercise filesystem and collection-level checks that cannot be represented by an isolated JSON mutation.
