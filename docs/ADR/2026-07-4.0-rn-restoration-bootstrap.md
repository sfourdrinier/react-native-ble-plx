# ADR: Unified BLE 4.0 React Native restoration bootstrap

**Status:** Accepted design baseline
**Date:** 2026-07-25

## Decision

Apple restoration is a pre-JavaScript ownership path. A code-owned native
provider creates or adopts exactly one `CBCentralManager` for each approved
restoration identity before JavaScript manager construction. The later native
backend factory authenticates that configured identity, adopts the existing
native owner, negotiates the applicable boundary versions, and reconstructs
bounded restoration records. It never creates a second central merely because
JavaScript starts, reloads, retries, or observes a record.

The production declaration shape is
[`restoration.ts`](../../src/backend-contract/restoration.ts) plus
[`host/react-native.ts`](../../src/backend-contract/host/react-native.ts).
The public API remains host-neutral; mobile construction/restoration are
explicit host setup, not root-import side effects.

## Bootstrap and adoption protocol

1. Bare-project configuration and the config plugin declare approved restoration
   identifiers before process launch. Background/restoration remain opt-in; the
   library never grants permissions or makes a host service exported.
2. Native startup validates the configured identity against code-owned bootstrap
   configuration, creates/retains the one central, and records its backend
   instance, attachment, adapter/backend generation, native-protocol range, and
   bounded journal metadata. Caller-supplied IDs cannot select an arbitrary
   existing native owner.
3. The JavaScript host factory presents the expected configured restoration
   identity and negotiated version range. Native rejects mismatch, duplicate
   adoption, consumed journal, incompatible version, or owner replacement with
   a typed error; it does not create a replacement central.
4. A successful adoption returns ordered, versioned, serializable journal
   records once. It reports existing state; it does not automatically reconnect,
   recreate subscriptions, resume an operation, or transfer another client's
   ownership. The application explicitly chooses any later policy.

The journal has a declared record and byte capacity, monotonic ordinal, explicit
overflow result, attachment/backend generation, safe payload schema, and
exactly-once consumption state. Early callbacks enter the same bounded journal;
after consumption they are delivered only through the negotiated bounded event
stream. Raw byte identity and callbacks never cross the JavaScript/native
boundary as durable state.

The handshake independently negotiates backend-contract, capability-schema,
event-schema, trace-format, and native-protocol axes; IPC is not implied by this
mobile boundary. No range overlap, malformed/unknown required record, or
downgrade is accepted. Every terminal error uses the shared dotted taxonomy.

## Lifecycle, cancellation, and generations

The restoration provider may outlive a borrowing JavaScript manager. Destroying
that borrower releases only its scan, connection, subscription, operation, and
listener leases. An owning manager may destroy the provider only when it owns
the approved native lifetime; otherwise explicit host shutdown owns that step.
Repeated destroy/adoption/cleanup returns the same terminal record.

Process restart, native replacement, adapter reset, journal overflow, or
restoration identity change advances the attachment/backend generation and
invalidates every old connection, database, path, operation correlation, and
subscription. Reload requires a fresh handshake and explicit rebind; late
native callback data is validated, released, and suppressed. Abort/deadline and
native cancellation use the shared `operation.aborted`/`operation.timed-out`
race rules, never public transaction IDs.

## Boundary, privacy, and security requirements

Restoration uses the one owned versioned C++ JSI binary boundary selected in the
[boundary ADR](2026-07-4.0-boundary.md); supported Codegen is control/bootstrap
only. Normal payloads do not use Base64, a second bridge, or fallback. Every
record is validated for native protocol, attachment, configured owner,
generation, capacity, and schema before it enters core state.

Restored device identifiers, names, GATT payloads, and platform messages are
sensitive. The provider stores only the minimum redacted/reconstructible state,
does not treat an identifier as peripheral authentication, and does not export
journal contents or diagnostics without explicit caller-requested policy.

## Export and native-artifact impact

Restoration construction is available only through the explicit mobile host
subpath. The root neither creates a central nor imports a mobile runtime. The
native bootstrap/JSI artifacts are package-controlled and version/ABI checked;
a missing or incompatible artifact fails the host factory without substituting
a second central, legacy bridge, mock, or text-encoded byte path.

## Rejected alternatives

- Constructing a second central during JavaScript initialization or restoration
  diagnostics: rejected because it races OS restoration and breaks radio
  ownership.
- Silent restore/reconnect/subscription resumption: rejected because ownership,
  consent, generations, and product reconnect policy must remain explicit.
- Unbounded early-event queue, cached object reference, native numeric handle,
  or user-provided global transaction ID: rejected because restart and hostile
  callback handling cannot be proven safe.

## Consequences and gates

Tests must prove cold launch without restoration, pre-JS callbacks, one owner,
duplicate/mismatched identity rejection, journal bounds/overflow, exact replay,
adoption race, owning/borrowing destroy, reload/restart generation barriers,
stale paths, cancellation/late events, and no duplicate subscriptions. Android
and Apple integration, Expo CNG and bare configuration, control/bootstrap
Codegen, the JSI binding, and physical restoration behavior require their own
platform evidence; missing hardware lowers only that evidence label.

The draft declarations were deleted at G1 promotion. Transitional restoration
wrappers, temporary managers, and fallback paths are removed at the same
cutover gate; they cannot coexist as a compatibility lane.
